# 플러그인 관리

관리자는 `/plugin-market.html`에서 플러그인을 찾아 설치하고, `/plugin-manage.html`에서 설치 버전, 실행 상태와 재시작 요구를 확인합니다. 로컬 패키지도 관리 페이지에서 업로드합니다. 설치 뒤에는 실제로 로드된 버전을 확인하세요. 디스크에 새 버전이 있어도 프로그램을 완전히 다시 시작해야 적용될 수 있습니다.

## 플러그인 설치하기

1. 마켓에서 신뢰하는 저장소를 선택하거나 관리 페이지에서 로컬 패키지를 선택합니다.
2. 용도, SDK 요구 사항, 출처, 의존성과 실행 모드를 확인합니다.
3. 설치 계획을 확인합니다. 실행 신뢰 확인이 추가로 나오면 게시자 지문이나 정확한 패키지 해시를 확인합니다.
4. 결과에 안내된 재시작을 마친 뒤 관리 페이지의 로드 버전과 해당 기능 페이지를 확인합니다. 실패했다면 반복 설치 전에 원래 작업 결과를 조회합니다.

GUI의 설정 → 플러그인 마켓 설정에서 사용자 지정 저장소를 추가하거나 편집합니다. 대화 상자 위쪽에서 ‘저장소 설명자 사용’과 ‘직접 입력’을 전환할 수 있습니다. 설명자 방식은 게시자, 연결 호스트, 공개 키의 전체 지문을 확인한 뒤 설정 초안에 추가합니다. 직접 입력에서는 URL, 네트워크 정책과 신뢰할 키를 설정합니다. 설정을 저장하고 다시 시작하면 적용됩니다. Web 마켓은 플러그인 탐색과 설치에 사용합니다.

## 변경 확인과 설치 결과 조회

마켓은 대상 패키지, 의존 패키지의 출처와 버전, 공유 의존성을 사용하는 플러그인, 충돌과 재시작 영향을 함께 표시합니다. 확인 후 실행 전에 다시 검사하며 상태가 바뀌면 미리보기를 갱신하고 재확인해야 합니다. 카탈로그에 새 패키지의 수명 주기 정보가 없으면 재시작 가능성만 안내하므로 실제 설치 결과를 따르세요.

의존 패키지는 순서대로 각각 별도 트랜잭션으로 설치됩니다. 상위 패키지가 실패해도 이미 성공한 의존 패키지는 남으며 결과에 버전과 `transactionId`가 표시됩니다. 일부 성공을 전체 롤백으로 해석하지 말고 관리 페이지에서 상태를 확인하세요.

작업 기록은 다운로드 준비부터 설치 종료까지 이어집니다. 페이지를 닫아도 이미 시작한 백엔드 요청은 취소되지 않으며 다시 열어 원래 작업을 조회할 수 있습니다. 같은 작업 ID의 재실행은 기존 상태만 반환합니다. 기록은 현재 프로세스에만 최대 64개, 비활성 기록은 최대 24시간 보관합니다. 프로세스 재시작, 만료 또는 기록 퇴출 후에는 결과를 알 수 없습니다. 설치 버전, 진단과 트랜잭션 상태를 확인한 뒤 새 작업을 명시적으로 시작하세요. 조회 실패로 자동 재설치하지 않습니다.

## 업데이트 알림과 이전 버전

다운로드 페이지 탐색 메뉴의 숫자 배지는 설치된 플러그인에 호환 업데이트가 있음을, 느낌표는 더 높은 SDK가 필요한 새 버전이 있음을 뜻합니다. 호환 알림은 SDK와 현재 마켓 정책이 후보를 허용한다는 의미입니다. 의존성과 실제 설치 조건은 설치할 때 다시 검사합니다. 관리 페이지 배너는 두 종류의 알림을 구분하며 같은 플러그인에 둘 다 표시될 수 있습니다. 검사 실패도 따로 표시하며 자동으로 다운로드하거나 설치하지 않습니다.

안정 버전 플러그인은 기본적으로 안정 업데이트만 추천합니다. 특정 시험판을 수동 설치한 뒤에야 해당 플러그인이 그 채널을 따르며 더 높은 안정 버전으로도 올라갈 수 있습니다. 주 프로그램이 Beta라고 플러그인 채널이 바뀌지는 않습니다. 다른 버전은 마켓 상세에서 직접 선택할 수 있습니다. 유지 관리자가 `-f`로 같은 버전의 패키지를 복구한 경우 일반 업데이트 배지는 나타나지 않으므로 복구 안내에 따라 재설치해야 합니다.

공식 기본 목록은 최신 버전, 최신 안정 버전, 지정된 구형 클라이언트 SDK 각각의 최신 호환 안정 버전을 보존합니다. 이 SDK 집합은 배포 저장소의 마켓 정리 설정에서 관리하며 현재 `1.0.0`, `1.1.0`을 포함합니다. 새 SDK가 나와도 자동으로 확대되지 않습니다.

나머지 버전 기록은 필요할 때 읽습니다. 호환 버전이나 현재 채널 후보를 찾을 때도 기록을 조회할 수 있습니다. 후보가 없는 경우와 기록 조회 실패는 따로 표시합니다. 이전 버전을 선택해도 같은 출처, 서명과 설치 검사를 거칩니다. 기록 파일은 해시로 이름을 정하며 이전 파일은 자동 삭제하지 않습니다. 단일 기록 목록이 900개 버전 또는 1 MiB 한도에 도달하면 배포를 중단하고 유지 관리자의 처리를 요구합니다.

## 마켓에서 설명 읽기

콘텐츠 표시를 지원하는 버전의 상세 화면에는 아이콘, 스크린샷과 작성자 링크가 나옵니다. 버전을 선택한 뒤 README, 이번 업데이트 설명 또는 전체 CHANGELOG를 펼칠 수 있습니다. 문서는 필요할 때 읽으며 실패하면 재시도할 수 있습니다. 이전 카탈로그는 기존 홈페이지와 일반 텍스트 업데이트 설명을 계속 표시합니다.

HTML과 Markdown은 정적 문서로 표시합니다. 문서의 스크립트, 폼, 이벤트 처리기와 사용자 지정 스타일은 실행하지 않습니다. 이미지는 해시를 검증한 버전 첨부 파일에서 가져오며 본문이 작성자의 임의 이미지 주소에 브라우저를 직접 연결하지 않습니다. 외부 링크는 사용자가 클릭해야 열립니다. 현재 언어를 우선하고 작성자의 기본 언어와 사용 가능한 대체 언어를 사용합니다.

이 설명은 용도 판단을 돕지만 출처 검증, 호환성이나 철회 상태 검사를 대신하지 않습니다. 표시 가능한 콘텐츠는 작성자의 제출물, 커뮤니티 도구 배포와 주 프로그램 버전에 따라 다릅니다. 라이선스와 커뮤니티 등록 조건은 [플러그인 개발 문서](/ko/plugin-development)를 참고하세요.

## 실행 보안

서명은 게시자 신원과 아티팩트의 바이트 무결성을 증명할 뿐 안전성 검토나 추가 실행 권한을 부여하지 않습니다. 신뢰하는 게시자와 저장소의 플러그인만 설치하세요.

호스트는 로드 전에 패키지 크기, 압축률, 경로와 JAR/ZIP 구조를 검사합니다. `plugin.properties`의 ID, 버전, 코어 API 요구 사항과 의존성, SHA-256, 구조화된 Ed25519 서명과 출처 증명(provenance), API 호환성과 필수 플러그인 제약도 확인합니다. 검증, 설명자 해석과 로드는 크기가 제한된 같은 고정 바이트를 사용합니다. 검증 뒤 다른 프로세스가 바꿀 수 있는 공개 설치 경로를 다시 열지 않습니다.

### 실행 모드와 격리 범위

모든 외부 플러그인은 `plugin.properties`에 `pixiv.execution-mode`를 명시해야 합니다.

| 값 | 실행 위치 | 권한 범위 |
| --- | --- | --- |
| `host-process-full-trust` | 호스트 JVM | 호스트 프로세스의 파일, 네트워크와 OS 권한을 상속 |
| `declarative-process` | 별도 worker JVM | 제한된 프로토콜로 선언형 라우트와 capability만 게시 |

값이 없거나 비어 있거나 알 수 없으면 플러그인 코드 실행 전에 거부됩니다. worker도 호스트와 같은 OS 계정을 사용하므로 프로세스, 프로토콜과 리소스 수준의 제한적 격리만 제공합니다. 완전한 OS 샌드박스나 이를 요구하는 JVM 스위치는 없습니다. 프로덕션 모드는 디렉터리 형태의 `declarative-process` 플러그인을 거부합니다. 명시적 개발 모드는 이를 `host-process-full-trust`로 전환하고 상태와 로그에 실제 모드를 표시합니다.

게시자가 같아도 `declarative-process`에서 `host-process-full-trust`로 바꾸거나 SDK 주 버전이 바뀌거나 신뢰가 철회된 뒤에는 관리자가 다시 확인해야 합니다. 호스트가 관리자 등 높은 권한으로 실행되면 full-trust 플러그인도 그 권한을 상속하며 관리 페이지에 경고가 계속 표시됩니다.

worker 기본값은 heap 128 MiB, metaspace 128 MiB, direct memory 64 MiB이며 OOM 시 종료됩니다. 초기화, 명령, 종료 제한 시간은 10,000 / 5,000 / 2,000 ms입니다. 비정상 종료 뒤 최대 3회 다시 시작하며 지연은 500 ms에서 최대 10,000 ms까지 증가합니다. stderr는 최대 1 MiB를 읽고 마지막 16 KiB를 보존합니다. worker마다 실행 중 1개와 대기 중 1개 요청만 허용합니다. 종료하면 호스트가 먼저 라우트와 capability를 철회한 뒤 이 한도 내에서 복구를 시도합니다.

JVM 시작 전에 `pixivdownload.plugin-worker.*`의 `initialize-timeout-ms`, `command-timeout-ms`, `shutdown-timeout-ms`, `restart-attempts`, `restart-initial-delay-ms`, `restart-max-delay-ms`, `stderr-max-bytes`로 해당 값을 조정할 수 있습니다.

### 패키지 수락 한도

기본값은 아카이브 192 MiB, 엔트리 48,000개, 실제 전체 압축 해제 672 MiB, 단일 엔트리 64 MiB, 설명자 1 MiB, 압축률 200(64 KiB 이상인 엔트리만 검사), 엔트리 이름 1,024자, 경로 깊이 64입니다.

- `pixivdownload.plugin.package.max-archive-bytes`
- `pixivdownload.plugin.package.max-entries`
- `pixivdownload.plugin.package.max-total-uncompressed-bytes`
- `pixivdownload.plugin.package.max-entry-uncompressed-bytes`
- `pixivdownload.plugin.package.max-descriptor-bytes`
- `pixivdownload.plugin.package.max-compression-ratio`
- `pixivdownload.plugin.package.max-entry-name-length`
- `pixivdownload.plugin.package.max-entry-depth`

대응하는 JVM 속성에는 양의 정수만 지정할 수 있습니다. 잘못된 값은 기본값으로 대체되지 않고 플러그인 런타임 초기화를 실패시킵니다.

## 상태 확인

카드는 넓은 창에서 여러 열, 좁은 창에서 한 열로 표시되며 이름, 용도, 실행 상태, 활성화 설정과 가능한 작업을 보여 줍니다. 상세 보기를 열면 디스크의 설치 버전, 현재 프로세스가 로드한 버전, SDK 요구 사항, 의존성과 출처 검증 정보를 확인할 수 있습니다. 검증 요약과 철회 시각은 필요할 때 펼칩니다. 업데이트나 제거 뒤 설치 버전과 로드 버전이 다를 수 있으므로 전체 재시작 안내를 따르세요.

‘현재 프로세스에 로드되지 않음’, ‘의존하는 플러그인 없음’, ‘정보를 사용할 수 없음’은 각각 미로드, 빈 의존성 목록, 해당 사실 조회 실패를 뜻합니다. 삭제나 비활성화 확인 창에는 목표 상태와 영향을 받는 의존 플러그인이 표시됩니다.

데스크톱 provider의 플러그인 페이지는 같은 백엔드 상태를 읽기 전용으로 표시합니다. 설치, 제거와 활성화 변경은 Web 관리 페이지에서 수행합니다.

## 설치 출처

### 배포 패키지에 포함된 플러그인

Windows 설치 프로그램과 Java 표준 패키지는 `plugins/`에 기본 공식 플러그인을 포함합니다. 필수 `download-workbench`, 기본 데스크톱 `gui-compose`와 대체 `gui-swing`도 들어 있습니다. full-offline 패키지는 공식 선택 플러그인까지 포함합니다. [PixivBatchDownloader 가져오기](/ko/pixiv-batch-downloader-import)는 일반 패키지에는 없고 오프라인 전체 패키지에는 포함되는 선택 플러그인입니다. Douyin은 사용자 지정 저장소나 로컬 패키지에서 설치하는 일반 타사 플러그인입니다. 기본 제공 플러그인도 코어 Boot JAR과 분리된 아티팩트입니다.

### 로컬 업로드

관리 페이지에서 `.jar` 또는 지원되는 `.zip`을 선택하고 필요하면 detached `.sig`를 함께 제공합니다. 서명이 있으면 정확한 아티팩트와 일치하고 적용되는 신뢰 루트로 검증되어야 합니다. 서명되지 않은 패키지는 `LOCAL_UPLOAD / UNSIGNED_ALLOWED`로 기록됩니다. 로컬 업로드는 사용자 지정 신뢰 루트를 만들지 않습니다.

비공식 로컬 패키지는 프로덕션 모드에서도 설치할 수 있지만 코드 실행 전에 위험 확인이 필요합니다. 서명된 패키지는 게시자 지문을, 서명되지 않은 패키지는 현재의 정확한 SHA-256만 승인합니다. 업데이트, 키 변경, 철회 또는 실행 권한 상승 시 다시 확인할 수 있습니다. 원격 저장소 패키지는 목록이 선언한 서명이 항상 필요하며 로컬 unsigned 처리로 전환되지 않습니다. 자체 키를 지속적으로 신뢰하는 타사 배포에는 사용자 지정 저장소를 설정하세요.

개발 모드에서도 설치 폴더의 플러그인을 불러옵니다. 실행 중인 소스 플러그인과 충돌하는 패키지는 저장만 하고 활성화하지 않습니다. 소스를 계속 사용하려면 충돌하는 패키지를 설치 폴더 밖으로 옮기고, 패키지를 사용하려면 개발 빌드에서 해당 소스 모듈을 제외한 뒤 앱을 재시작하세요.

### 플러그인 마켓

마켓과 내장 공식 저장소는 기본적으로 활성화됩니다. 시작 자체는 저장소에 연결하지 않지만 관리자 페이지의 업데이트 검사, 마켓 열기·새로고침과 설치는 요청을 보낼 수 있습니다. `plugin-catalog.enabled`로 끌 수 있습니다. 공식 저장소는 프로그램 내장 주소와 신뢰 루트를 사용합니다. 사용자 지정 저장소는 `config.yaml`에 자체 HTTPS manifest와 Ed25519 공개 키를 설정합니다. [설정 참고](/ko/configuration)를 확인하세요.

최신 버전이 현재 SDK와 호환되지 않으면 같은 저장소에서 설치 가능한 가장 높은 호환 이전 버전을 찾고 기본 선택을 카드와 상세 화면에 표시합니다. ‘현재 버전과 호환되는 항목만’ 필터도 이 플러그인을 유지합니다. 상세에서 이전 버전을 직접 선택할 수도 있습니다. 호환 버전 없음과 조회 미완료는 구분하며 후자는 새로고침으로 재시도할 수 있습니다. 설치에는 확인이 필요하며 이미 설치한 높은 버전을 자동으로 내리지 않습니다.

| 상태 | 의미 |
| --- | --- |
| `NOT_INSTALLED` | 설치할 수 있는 호환 버전이 있음 |
| `INSTALLED` | 설치되어 있으며 엄격히 더 높은 호환 버전은 없음 |
| `UPDATE_AVAILABLE` | 엄격히 더 높은 호환 버전이 있음 |
| `INCOMPATIBLE` | 현재 SDK를 만족하는 설치 가능 버전이 없음 |
| `UNAVAILABLE` | 설치할 아티팩트가 없거나 호환 버전 조회가 끝나지 않음. 화면 설명 확인 |

상세 화면 위쪽에는 용도, 설치 상태와 설치 작업이 나옵니다. 설치됨, 활성화됨 또는 재시작 대기 상태라면 관리 페이지로 이동할 수 있습니다. 아래에는 설명과 버전 요구 사항이 있으며 출처, capability 선언, 검증 정보와 변경 기록을 펼칠 수 있습니다.

설치 진행은 계획 검사, 확인 대기, 설치 중으로 구분합니다. 확인 대기는 설치가 시작되었다는 뜻이 아닙니다. 계획 확인을 취소하면 계획을 실행하지 않지만 이후 실행 신뢰 확인을 취소하면 이미 성공한 의존 패키지는 남습니다. 작업 기록은 백엔드 다운로드·설치 상태를 저장하므로 최종 적용 여부는 설치 결과와 실제 런타임 상태를 함께 확인하세요.

## 설치와 업데이트 트랜잭션

로컬 업로드와 마켓 설치는 같은 순서를 따릅니다.

1. 후보 아티팩트를 한도 내에서 읽고 바이트를 고정합니다.
2. 구조, 설명자, API, 의존성, 해시, 서명과 출처를 검증합니다.
3. 기존 generation의 새 요청 접수를 중단하고 진행 중인 작업이 끝나기를 기다립니다.
4. 아티팩트와 provenance를 원자적으로 교체합니다.
5. 수명 주기 정책에 따라 새 패키지를 활성화합니다.
6. 어느 단계든 실패하면 이전 아티팩트, provenance와 사용 가능한 generation을 복구합니다.

업데이트는 기존 클래스 인스턴스에 패치를 적용하는 대신 트랜잭션으로 교체합니다. 작업 뒤 상태를 다시 읽어 실제 적용 여부를 확인하세요.

## 수명 주기 정책

`plugin.properties`의 `pixiv.lifecycle-policy`는 다음 세 값만 허용합니다. 대소문자를 구분하며 생략하면 `hot-reload`입니다.

| 값 | 설치·업데이트 | 활성화·비활성화 | 적용 대상 |
| --- | --- | --- | --- |
| `hot-reload` | 현재 프로세스에서 트랜잭션 교체 후 즉시 활성화 | 직접 start/stop | 기여 항목을 완전히 철회하고 작업·클라이언트를 해제할 수 있는 플러그인 |
| `backend-restart` | 현재 프로세스에서 트랜잭션 교체 후 즉시 활성화 | 설정 저장 후 백엔드 재시작 안내 | 데스크톱 프로세스 종료 없이 Spring 백엔드 컨텍스트를 다시 만들어야 하는 플러그인 |
| `process-restart` | 패키지를 안전하게 저장하고 전체 프로세스 재시작 뒤 활성화 | 설정 저장 후 프로그램 재시작 안내 | 데스크톱 provider, 테마, 트레이처럼 프로세스 수준 구성 요소가 오래 보유하는 기능 |

백엔드 재시작은 Spring 컨텍스트만 다시 만듭니다. `process-restart` 플러그인은 적용할 수 없습니다. 데스크톱 수명 주기 관리자를 사용할 수 없다면 관리 페이지가 운영체제를 대신해 프로세스를 재시작할 수 없습니다.

공식 `gui-compose`가 기본 데스크톱 provider이고 `gui-swing`이 자동 대체 provider입니다. 각자 페이지와 상호작용을 소유하고 애플리케이션의 비즈니스 의미를 공유합니다. 둘 다 `process-restart`이므로 설치, 업데이트, 활성화 변경, 제거 또는 설정 → 인터페이스에서 provider를 변경한 뒤 프로그램을 완전히 종료하고 다시 시작해야 합니다.

## 수명 주기 작업

관리 가능한 `hot-reload` 외부 플러그인에는 다음 여덟 작업이 있습니다.

| 작업 | 동작 |
| --- | --- |
| `load` | 설치된 아티팩트에서 클래스 로더와 플러그인을 만들지만 실행 기능은 아직 게시하지 않음 |
| `start` | 로드된 플러그인을 시작하고 자식 컨텍스트와 기여 항목을 게시 |
| `quiesce` | 새 작업 접수를 중단하고 현재 publication의 작업·호출이 끝나기를 기다림 |
| `stop` | 기여 항목을 철회하고 인스턴스를 중지하며 설치 패키지는 유지 |
| `unload` | 중지 뒤 PF4J 플러그인과 클래스 로더를 해제하며 설치 패키지는 유지 |
| `remove` | 안전하게 종료한 뒤 설치된 아티팩트와 provenance를 삭제 |
| `restart` | 현재 인스턴스를 stop/start하며 generation과 클래스 로더는 유지 |
| `reload` | quiesce, stop, unload 뒤 load/start하여 새 generation과 클래스 로더 생성 |

`purge` 작업은 없습니다. 제거에는 `remove`를 사용합니다. 플러그인의 `config/`, `state/`, `data/` 보존은 별도 데이터 보존 정책을 따릅니다.

선택 사항인 `process-restart` 플러그인도 관리 페이지에서 제거할 수 있습니다. 설치된 패키지와 출처 증명을 삭제하고 설정, 자격 증명, 데이터베이스, 상태와 다운로드 파일은 보존합니다. 현재 프로세스가 플러그인을 로드했다면 전체 재시작 전까지 기존 인스턴스는 계속 실행됩니다. 필수 플러그인과 활성 의존 플러그인이 있는 대상은 제거할 수 없습니다.

업데이트나 제거 뒤에는 디스크 설치 상태와 현재 프로세스의 로드 버전을 구분해 표시합니다. 새 패키지는 자체 내용과 provenance로 검증하며 기존 인스턴스의 검증 결과를 대신 쓰지 않습니다. 재설치 뒤에도 보존한 데이터를 사용할 수 있습니다.

클래스를 바꾸지 않고 서비스를 다시 만들 때는 `restart`를, 코드나 리소스 아티팩트가 바뀌었다면 `reload`를 사용합니다. 비동기 플러그인의 `quiesce`는 실제 양의 generation에 연결된, 기다릴 수 있는 drain을 반환해야 합니다. 백그라운드 작업이 남아 있는데 완료 표식을 반환해서는 안 됩니다.

## 활성화 설정과 필수 플러그인

활성화 설정은 `config/config.yaml`의 `plugins.{pluginId}.enabled`에 저장합니다. `hot-reload`는 바로 start/stop하고 나머지는 저장 뒤 필요한 재시작을 안내합니다.

필수(required) 플러그인을 비활성화하거나 제거하여 요구 조건을 깨뜨릴 수 없습니다. 필수 패키지가 없거나 손상·비호환·오프라인 재검증 실패·시작 실패 상태라면 코어 셸은 관리와 복구 입구를 유지한 복구 모드로 들어갑니다. 선택 플러그인의 실패는 보통 해당 기능만 격리하지만 현재 선택된 주 데이터베이스 provider를 사용할 수 없어도 주요 기능이 준비되지 않습니다. 마켓 배너는 사용할 수 없는 필수 플러그인과 진단을 표시하고 복구할 기본 설치 플러그인을 안내합니다.

`plugin.dependencies`는 PF4J 의존성 표현식을 사용합니다. 호스트는 설치·시작 전에 플러그인 존재 여부, 버전과 의존성 그래프를 검사합니다. 공유 의존성을 업데이트하기 전에 모든 소비 플러그인의 버전 범위를 확인하세요. `plugin.requires`는 주 프로그램의 제품 버전이 아니라 필요한 코어 API 버전입니다. 호환되지 않는 미설치 패키지는 `INCOMPATIBLE`로 표시하고 로드하지 않습니다.

## 파일 경계

설치 신원은 `plugins/` 루트의 원본 아티팩트와 `plugins/provenance/` sidecar로 구성됩니다. `plugins/runtime/`은 generation별 비공개 고정 작업 영역입니다.

- 실행 중에 JAR을 수동 덮어쓰지 마세요.
- `plugins/runtime/`을 설치 디렉터리, 서명 원본이나 공유 캐시로 사용하지 마세요.
- 원격 출처 패키지를 복사할 때 provenance를 빠뜨리지 마세요.
- 개인 키를 `plugins/`, 소스, 빌드 결과나 로그에 넣지 마세요.

portable 설치는 `plugins/` 루트 자체를 심볼릭 링크나 Windows junction으로 둘 수 있습니다. 런타임은 실제 루트를 먼저 해석해 고정하지만 그 안의 링크된 아티팩트는 개별적으로 거부합니다. 지원되는 파일 시스템에서는 `plugins/runtime/`과 `plugins/provenance/`의 POSIX 권한 또는 Windows ACL을 제한합니다. FAT32, exFAT, SMB 등이 이를 지원하지 않으면 진단을 남기고 일반 파일, `NOFOLLOW`, 고정 스냅샷과 해시 검사를 계속 사용합니다. 전체 배치는 [저장 원칙](/ko/storage)을 참고하세요.

## 문제 해결과 복구

설치는 성공했는데 페이지가 없다면 응답의 `effectiveAfterRestart`와 정책을 확인하세요. `process-restart`는 브라우저 새로고침이나 백엔드 재시작으로 적용되지 않습니다. 다른 정책은 관리 페이지를 새로고침해 `STARTED`와 기여 등록 진단을 확인합니다.

비호환이면 `plugin.requires`, `requiredCoreApi`와 의존 플러그인 버전을 확인합니다. 설명자를 고쳐 검사를 우회하지 말고 호스트를 업데이트하거나 게시자의 호환 버전을 설치하세요. 서명이나 provenance 실패는 원래 저장소에서 다시 다운로드해 확인합니다. 원격 패키지의 서명 누락, 알 수 없거나 철회된 키, 해시 불일치, 아티팩트와 sidecar 불일치는 설치를 거부하며 unsigned로 전환하지 않습니다.

`stop`이나 `reload`가 계속 기다린다면 활성 호출, 큐 작업, HTTP/WebSocket 클라이언트나 스케줄러를 로그에서 확인하세요. 작성자는 새 요청을 중단하고 작업을 취소하거나 drain을 기다리며 자식 컨텍스트 종료 때 자체 클라이언트, 실행기와 스케줄러를 해제해야 합니다.

제거 후 설정이 남는 것은 데이터 보존 동작입니다. `remove`는 `config/plugins/{id}.properties`, 암호화된 자격 증명이나 owner 데이터를 지우지 않습니다. 더 이상 필요 없고 백업했다면 프로그램을 중지한 상태에서 해당 owner의 데이터만 정리하세요.

시작에 실패한 외부 플러그인 카드의 패키지 교체 복구 버튼은 기존 업로드 창을 엽니다. 같은 플러그인 ID의 호환 복구 패키지를 선택하고 검증과 위험 확인을 완료합니다. 필수 플러그인은 교체할 수 있지만 제거할 수 없습니다. 선택 플러그인 제거도 의존성과 수명 주기 검사를 따릅니다. 교체·제거는 설정, 데이터와 미완료 작업을 보존하며 자체 데이터 마이그레이션은 플러그인이 담당합니다.

## 철회 정보와 실행 중인 인스턴스

관리 페이지는 마지막 성공 갱신 시각, 문서 유효 기한, 유예 기한과 제한 사유를 표시합니다. 관리자는 설정된 활성 출처를 직접 갱신할 수 있습니다. 마켓 탐색과 설치도 기존 흐름에 따라 갱신합니다. 일반 상태 조회는 연결하지 않으며 백그라운드 정기 갱신도 없습니다. 오프라인이나 갱신 실패 시 마지막으로 검증한 유효 스냅샷을 보존하므로 실패를 ‘제한 없음’으로 해석하면 안 됩니다.

`YANKED`는 새 설치와 업데이트를 차단하고 `REVOKED`는 이후 로드와 시작도 차단합니다. 유효한 스냅샷이 없거나 24시간 유예가 지나면 새 설치를 거부합니다. 현재 프로세스는 기존 인스턴스를 계속 보유할 수 있으며 철회 갱신은 full-trust 코드를 강제 종료하지 않습니다. 중지하려면 앱을 완전히 종료하고 복구 상태를 확인한 뒤 다시 시작하세요.

플러그인 제작, 다운로드 유형이나 독립 갤러리 확장은 [타사 플러그인 SDK](/ko/plugin-development)를 참고하세요. 템플릿에서 시작하고 애플리케이션 셸 구현 클래스를 복사하지 마세요.
