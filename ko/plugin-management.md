# 플러그인 관리

관리자는 `/plugin-market.html`에서 플러그인을 찾아 설치하고 `/plugin-manage.html`에서 설치 버전, 현재 프로세스의 로드 상태와 재시작 요구를 확인하거나 로컬 플러그인 패키지를 업로드할 수 있습니다. 디스크에 설치됐다고 현재 프로세스에 로드된 것은 아닙니다. 일부 플러그인은 백엔드 재시작이나 프로그램 완전 종료 후 재실행이 필요합니다.

## 플러그인 설치 및 사용자 정의 저장소

1. 플러그인 마켓의 신뢰하는 저장소에서 플러그인을 선택하거나 관리 페이지에 로컬 `.jar` / `.zip`을 업로드합니다. `.sig`를 함께 첨부할 수 있습니다.
2. 플러그인 용도, 필요한 SDK 버전, 출처, 의존성과 실행 모드를 확인합니다.
3. 설치 계획의 대상 패키지, 의존성 출처와 버전, 역방향 소비자, 충돌과 재시작 영향을 확인하고 승인합니다. 실행 신뢰 확인이 나타나면 게시자 공개 키 지문이나 패키지 SHA-256을 확인합니다.
4. 결과 안내에 따라 필요한 재시작을 수행하고 관리 페이지에서 로드 버전과 기능 진입점을 확인합니다. 실패하면 원래 작업 기록을 먼저 확인하고 무작정 재설치하지 마세요.

데스크톱 GUI의 '설정 → 플러그인 마켓 설정'에서 사용자 정의 저장소를 추가하거나 편집할 수 있습니다. '저장소 설명자 사용'을 선택하면 게시자, 연결할 호스트와 공개 키 전체 지문을 미리 확인한 후 초안에 추가합니다. '직접 입력'은 HTTPS 매니페스트 URL, 프록시 정책과 Ed25519 공개 키를 입력합니다. 설정을 함께 저장하고 재시작하면 적용됩니다.

의존성은 순서대로 독립된 설치 트랜잭션을 사용합니다. 부모 패키지가 실패해도 성공적으로 설치한 의존성은 유지되며 결과에 버전과 `transactionId`가 표시됩니다. 마켓 작업 기록은 현재 프로세스 메모리에 저장합니다. 최대 64개이며 비활성 기록은 24시간 보존합니다. 페이지를 닫아도 시작한 백엔드 설치는 취소되지 않습니다. 프로세스 재시작이나 기록 만료 후에는 관리 페이지에서 실제 설치 상태를 먼저 확인하세요.

## 업데이트 안내 및 이전 버전

다운로드 페이지 탐색 영역의 숫자 배지는 설치한 플러그인에 호환 업데이트가 있음을, 느낌표는 더 높은 SDK가 필요한 새 버전이 있음을 뜻합니다. 관리 페이지 배너는 두 안내를 각각 표시합니다. 안정 버전 플러그인은 기본적으로 안정 업데이트만 추천합니다. 프리릴리스를 수동 설치한 후에만 해당 프리릴리스 채널을 따르며 더 높은 안정 버전으로도 업그레이드할 수 있습니다. 같은 버전의 수동 수정 패키지(`-f`)는 일반 업데이트 배지를 표시하지 않으므로 수정 안내에 따라 재설치해야 합니다.

공식 주 매니페스트는 최신 버전, 최신 안정 버전과 고정된 이전 SDK 집합(`1.0.0`, `1.1.0`)에 대한 최신 호환 안정 버전을 보관합니다. 나머지 이전 버전은 다이제스트로 이름 붙인 `history/` 매니페스트에 저장하며 파일당 최대 900개 버전 또는 1 MiB입니다. 기록을 보거나 호환되는 이전 버전을 자동으로 찾을 때 필요에 따라 로드합니다.

최신 플러그인이 현재 SDK와 호환되지 않으면 마켓이 같은 저장소에서 설치 가능한 가장 높은 호환 이전 버전을 자동으로 찾고 카드와 상세 정보에 기본 선택을 표시합니다. 상세 정보에서 정적으로 격리된 README, 이번 업데이트 설명이나 CHANGELOG를 펼쳐 보거나 이전 버전을 직접 선택할 수도 있습니다. 플러그인 라이선스와 커뮤니티 등록 규칙은 [서드파티 플러그인 SDK](/ko/plugin-development#플러그인-라이선스-및-배포-채널)를 참고하세요.

## 보안 모델 및 패키지 허용 상한

Ed25519 서명은 게시자 출처와 바이트 무결성을 증명하지만 코드 보안 검토나 운영체제 샌드박스 격리를 뜻하지 않습니다. 신뢰하는 게시자와 저장소의 플러그인만 설치하세요. 호스트는 로드 전에 상한을 적용하여 패키지를 전용 작업 공간에 고정하고 동일한 고정 바이트에 대해 패키지 구조, `plugin.properties`, SHA-256, 서명, provenance, SDK 호환성과 의존성을 검증합니다.

### 실행 모드

모든 외부 플러그인은 `plugin.properties`에 `pixiv.execution-mode`를 명시해야 합니다. 누락되거나 알 수 없는 값이면 코드 실행 전에 거부합니다.

| 값 | 실행 위치 | 격리 및 권한 경계 |
| --- | --- | --- |
| `host-process-full-trust` | 호스트 JVM | 호스트 프로세스의 파일, 네트워크와 운영체제 권한 상속. 호스트가 높은 권한으로 실행되면 관리 페이지에 경고 지속 표시 |
| `declarative-process` | 별도 worker JVM | 호스트 OS 계정을 공유하고 한도 있는 프로토콜로만 선언적 라우트와 기능 제공. 완전한 OS 샌드박스는 아님. 운영에서는 폴더 형태를 거부하며 개발 모드에서는 임시로 full-trust로 낮추고 실제 상태 표시 |

`declarative-process`에서 `host-process-full-trust`로 승격하거나 SDK 주 버전이 바뀌거나 신뢰가 취소되면 관리자가 신뢰를 다시 확인해야 합니다. worker의 기본 한도는 heap 128 MiB, metaspace 128 MiB, direct memory 64 MiB입니다. OOM이면 종료하며 최대 3회 자동 재시작하고 재시도 간격은 `500–10000` ms입니다. 초기화 / 명령 / 종료 시간 제한은 각각 `10000` / `5000` / `2000` ms이며 진행 중 요청 1개와 대기 요청 1개만 허용합니다. `pixivdownload.plugin-worker.*` JVM 속성으로 조정할 수 있습니다.

### 플러그인 패키지 기본 리소스 상한

| JVM 속성(접두사 `pixivdownload.plugin.package.`) | 기본 상한 |
| --- | --- |
| `max-archive-bytes` | 192 MiB |
| `max-entries` | 48,000개 항목 |
| `max-total-uncompressed-bytes` | 672 MiB |
| `max-entry-uncompressed-bytes` | 64 MiB |
| `max-descriptor-bytes` | 1 MiB |
| `max-compression-ratio` | 200. ≥ 64 KiB인 항목만 검사 |
| `max-entry-name-length` / `max-entry-depth` | 1,024자 / 폴더 64단계 |

이 속성들은 양의 정수만 허용하며 잘못된 값은 플러그인 런타임 초기화를 즉시 막습니다.

## 설치 출처 및 마켓 상태

- **배포 패키지 사전 설치**: Windows 설치 패키지와 Java 표준 패키지는 `plugins/`에 `download-workbench`, `database-sqlite`, `gui-compose`, `gui-swing`, `gallery`, `novel` 등의 기본 공식 플러그인을 포함합니다. 오프라인 전체 패키지에는 `database-postgresql`, [PixivBatchDownloader 가져오기 지원](/ko/pixiv-batch-downloader-import) 등의 선택적 공식 플러그인도 포함됩니다. `douyin`은 독립 서드파티 플러그인이며 사용자 정의 저장소나 로컬 패키지로만 설치합니다.
- **로컬 업로드**: 사용자 정의 신뢰 루트를 만들지 않습니다. 서명이 있으면 기존 신뢰 루트로 검증해야 하며 게시자 지문을 기준으로 승인합니다. 무서명 패키지는 `LOCAL_UPLOAD / UNSIGNED_ALLOWED`로 표시하고 현재의 정확한 SHA-256만 승인합니다. 원격 저장소 패키지는 매니페스트 서명이 필수이며 로컬 무서명으로 낮추지 않습니다. 개발 모드에서 설치 패키지와 소스 모듈의 이름이 충돌하면 패키지만 저장하고 활성화하지 않습니다. 충돌 패키지를 옮기거나 소스 모듈을 제외한 후 재시작해야 합니다.
- **마켓 상태 코드**: `NOT_INSTALLED`(설치 가능한 호환 버전 있음), `INSTALLED`(설치되어 있고 더 높은 호환 버전 없음), `UPDATE_AVAILABLE`(더 높은 호환 버전 있음), `INCOMPATIBLE`(현재 SDK와 호환되는 버전 없음), `UNAVAILABLE`(설치 가능한 산출물 없음 또는 호환 조회 미완료).

## 트랜잭션 교체 및 수명 주기 정책

설치와 업데이트는 원자적 트랜잭션을 사용합니다. 후보 바이트 고정 → 설명자/서명/의존성 검증 → 이전 세대의 새 요청 수락 중지 및 drain 대기 → artifact와 provenance 원자적 교체 → 정책에 따른 활성화 순서이며 실패하면 이전 세대로 완전히 롤백합니다.

| `pixiv.lifecycle-policy` | 설치 / 업데이트 | 활성화 / 비활성화 | 적용 플러그인 |
| --- | --- | --- | --- |
| `hot-reload`(기본값) | 현재 프로세스에서 즉시 교체 및 활성화 | 직접 start / stop | 기여 기능을 완전히 철회하고 백그라운드 작업과 클라이언트를 해제할 수 있는 플러그인 |
| `backend-restart` | 현재 프로세스에서 즉시 교체 및 활성화 | 상태 저장 후 백엔드 재시작 안내 | Spring 백엔드 컨텍스트 재구성이 필요한 플러그인 |
| `process-restart` | 디스크에 저장하고 프로그램을 완전히 종료한 후 재시작해야 활성화 | 상태 저장 후 프로그램 완전 재시작 안내 | `gui-compose`, `gui-swing`, 데이터베이스 provider, 계약 전달 플러그인과 테마 등 프로세스 단위 플러그인 |

관리 가능한 `hot-reload` 플러그인은 8가지 작업을 지원합니다. `load`, `start`, `quiesce`(새 요청 수락 중지 및 drain 대기), `stop`, `unload`, `remove`(설치 패키지와 provenance 삭제, `config/`, `state/`, `data/`의 업무 데이터 보존), `restart`(같은 세대 재시작), `reload`(새 generation과 classloader 생성)입니다. `purge` 작업은 없습니다.

## 복구 모드, 취소 정보 및 문제 해결

- **활성화 상태 및 복구 모드**: 스위치는 `config/config.yaml`의 `plugins.{pluginId}.enabled`에 저장합니다. 필수 플러그인이나 현재 선택한 주 데이터베이스 provider가 없거나 손상되거나 호환되지 않거나 시작에 실패하면 복구 모드로 들어가 로그인, 플러그인 관리와 '다른 패키지로 복구'만 유지합니다. 일반 선택적 플러그인의 오류는 해당 기능만 격리합니다.
- **취소 정보(`YANKED` / `REVOKED`)**: `YANKED`는 새 설치와 업데이트를 막고 `REVOKED`는 이후 로드와 시작도 막습니다. 유효한 취소 스냅샷이 없거나 24시간 유예 기간을 넘으면 새 설치를 금지합니다. 취소 정보 갱신은 현재 프로세스에서 실행 중인 full-trust 코드를 강제 종료하지 않습니다. 애플리케이션을 완전히 종료하고 복구한 후 다시 시작해야 합니다.
- **자주 발생하는 문제**:
  - **설치 후 페이지가 나타나지 않음**: 결과의 `effectiveAfterRestart`를 확인하세요. `process-restart` 플러그인은 프로그램을 완전히 종료하고 다시 열어야 하며 웹페이지 새로고침이나 백엔드 재시작만으로는 적용되지 않습니다.
  - **호환되지 않거나 서명 검증 실패**: `plugin.requires`(애플리케이션 버전이 아닌 필요한 SDK 버전)와 의존성 버전을 확인하고 원래 저장소에서 완전한 패키지를 다시 받으세요. `plugin.properties`를 수동 수정하지 마세요.
  - **`stop` / `reload`가 오래 대기함**: `log/latest.log`에서 종료되지 않은 대기열 작업, HTTP/WebSocket 클라이언트나 스케줄러 스레드가 있는지 확인하세요.

플러그인 파일 저장 구조는 [저장소 및 백업](/ko/storage), 서드파티 플러그인 개발은 [서드파티 플러그인 SDK](/ko/plugin-development)를 참고하세요.
